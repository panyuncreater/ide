# MiniLang IDE 毕业设计答辩思路

## 一、答辩核心主线（5 分钟陈述框架）

### 1. 开场定位（30 秒）
**一句话概括项目：**
> "MiniLang IDE 是一个从零实现的教学型编程语言开发环境，包含完整的词法分析器、递归下降解析器、三套独立执行引擎（树遍历解释器、栈式字节码 VM、寄存器式 VM）、IR 中间表示层、源码级调试器和基于 Qt6 的现代化 GUI，总计约 11 万行 C++20 代码。"

**设计动机：**
- 现有教学语言（如 Lox、Python）缺少完整的 IDE 支持
- 工业界编译器（LLVM、V8）过于复杂，不适合教学
- 目标：在可理解规模内，展示编译器 + 虚拟机 + 调试器的完整技术栈

---

### 2. 技术架构亮点（2 分钟）

#### 2.1 三后端执行管线（核心创新点）
```
源代码 → Lexer → Parser → AST → 
    ├─ (1) Interpreter（树遍历解释器，直接执行 AST）
    ├─ (2) Compiler → BytecodeChunk → VM（栈式虚拟机，75 条 OpCode）
    └─ (3) AstIRBuilder → IRModule → 
            ├─ BytecodeIRBackend → VM（栈式 VM 的 IR 路径）
            └─ RegisterBytecodeBackend → RegisterVM（寄存器式 VM，32 虚拟寄存器，59 条 RegOp）
```

**关键技术约束：**
- **三后端语义一致性**：同一 MiniLang 源码在三条路径上必须产生相同结果
- 整数除法截断向零、and/or 短路返回操作数原值（非布尔）、类型注解强制、super 调用语义等需统一
- IR 路径与非 IR 路径共享 VM，但中间表示不同（BytecodeChunk vs RegBytecodeChunk）

#### 2.2 内存模型设计
- **Value 采用 NaN-boxing**（8 字节）：用双精度浮点数的 NaN 位模式区分类型
- **堆类型通过侵入式 RefCounted 基类管理**：自动引用计数
- **数组/字典使用 Copy-On-Write（COW）**：写前检查独占所有权，避免不必要的复制
- **VM 操作数栈为定长数组 Value[1024]**：栈式 VM 的核心数据结构
- **寄存器帧使用 std::array<Value, 32>**：零堆分配，性能优化
- **Environment 链式作用域**：boundInstance_缓存优化变量查找

#### 2.3 模块化架构（ARCH-11 重构成果）
原 God Object 拆分为 4 个独立协作类：
| 类名 | 职责 |
|------|------|
| PipelineRunner | 词法/语法/编译/格式化管线 |
| WorkerManager | Worker 线程管理 + Interpreter/Debugger 所有权 |
| DebugCoordinator | 调试状态/回调/步进控制 |
| VmStepper | VM 单步执行状态机 |

**IdeController 作为 Facade**：持有 4 个协作类成员，转发公共 API 到对应协作类，协调跨类操作。

### 3. 核心技术挑战与解决方案（1.5 分钟）

#### 挑战 1：三后端语义一致性验证
**问题**：同一语言特性在三个执行引擎中实现不一致，导致难以排查的 Bug。

**解决方案**：
- 建立系统性审计流程：逐函数阅读 + 边界条件枚举 + 三后端交叉验证
- 实现 BackendComparePanel：自动化对比三后端执行结果
- 关键语义点清单：错误消息文本、类型检查行为、边界条件处理

#### 挑战 2：IR 路径栈不平衡
**问题**：表达式语句返回值未 POP 导致栈泄漏（曾出现 16 种节点类型遗漏）。

**解决方案**：
- 栈/寄存器平衡审计：每个 emit 路径的 push/pop 数量必须匹配
- 添加 BytecodeTracePanel：可视化追踪 VM 栈变化
- 单元测试覆盖所有 AST 节点类型

#### 挑战 3：闭包/Upvalue 生命周期管理
**问题**：多嵌套层捕获、变量快照恢复、闭包调用参数顺序容易出错。

**解决方案**：
- ClosureInspectorPanel：可视化查看闭包捕获的变量
- 资源生命周期追踪：每个 RAII guard、shared_ptr、raw pointer 的获取与释放配对审查
- 调试器支持闭包展开查看

#### 挑战 4：调试器条件断点的 UAF（Use-After-Free）问题
**问题**：沙箱状态恢复、缓存与一致性处理不当导致悬空指针。

**解决方案**：
- BreakpointConditionPanel：安全地管理和查看断点条件
- 沙箱状态完整保存/恢复机制
- 缓存失效时的一致性检查

#### 挑战 5：GUI 线程与 Worker 线程的竞态条件
**问题**：运行期间 UI 操作未禁用、原子标志竞态、Worker 状态清理不完整。

**解决方案**：
- 线程安全审查：识别所有跨线程数据访问
- isDebugPaused() 接口：面板在 autoTimer 触发前检查调试暂停状态
- Qt 事件清理：clearPendingEvents() 防止 UAF

### 2. 可能被问到的问题与回答

#### Q1: 为什么选择三后端架构？
**A**: 
1. **教学价值**：展示不同执行策略的权衡（解释器简单但慢，VM 快但复杂）
2. **一致性验证**：三后端互相校验，更容易发现语义 Bug
3. **工程实践**：模拟真实编译器的多后端设计（如 LLVM 的多目标后端）

#### Q2: NaN-boxing 的原理是什么？为什么选择它？
**A**: 
- **原理**：IEEE 754 双精度浮点数的 NaN 位模式有未使用的位，可以用来编码类型标签和整数/布尔值
- **优势**：所有 Value 统一为 8 字节，无需额外的类型标签字段；小整数和布尔值无需堆分配
- **劣势**：代码复杂度增加，需要频繁的类型解包检查

#### Q3: 寄存器式 VM 相比栈式 VM 有什么优劣？
**A**: 
- **优势**：
  - 指令数更少（不需要 PUSH/POP）
  - 更接近真实 CPU 架构，便于后续 JIT
  - 寄存器访问比栈访问更快（随机访问 vs 顺序访问）
- **劣势**：
  - 指令编码更复杂（需要指定操作数寄存器）
  - 寄存器分配算法复杂（本项目使用固定 32 寄存器简化设计）

#### Q4: 如何保证三后端的语义一致性？
**A**: 
1. **设计阶段**：定义明确的语义规范文档（整数除法、短路求值等）
2. **实现阶段**：共享前端代码（Lexer/Parser/AST），仅后端不同
3. **测试阶段**：BackendComparePanel 自动化对比，单元测试覆盖边界条件
4. **审计阶段**：系统性代码审查，逐函数对比三后端实现

#### Q5: 闭包的实现难点在哪里？
**A**: 
1. **Upvalue 捕获**：需要追踪变量在哪一层作用域被捕获
2. **生命周期管理**：闭包可能比创建它的作用域存活更久，需要引用计数
3. **变量共享**：多个闭包捕获同一变量时，需要共享同一个 Upvalue 对象
4. **调试支持**：调试时需要正确展开闭包捕获的变量

#### Q6: 调试器的单步执行是如何实现的？
**A**: 
- **解释器模式**：每执行一个 AST 节点，检查是否到达断点或需要步进
- **VM 模式**：VmStepper 状态机跟踪当前 IP，每执行一个 OpCode 后检查调试状态
- **关键点**：需要正确处理函数调用/返回时的步进逻辑（Step In/Over/Out 的区别）

#### Q7: 项目中遇到的最大 Bug 是什么？如何解决的？
**A**: 
（从 AGENTS.md 中选择 1-2 个典型案例）
- **案例 1**：IR 路径栈不平衡，16 种 AST 节点类型遗漏 POP 操作
  - **解决**：建立栈平衡审计清单，添加 BytecodeTracePanel 可视化追踪
- **案例 2**：条件断点的 UAF 问题
  - **解决**：完善沙箱状态保存/恢复机制，添加缓存一致性检查

#### Q8: 如果让你继续扩展这个项目，你会做什么？
**A**: 
1. **JIT 编译**：将热点代码编译为本地机器码（使用 asmjit 或 LLVM）
2. **类型推断**：可选的静态类型检查，提前发现类型错误
3. **并发支持**：轻量级协程或 Actor 模型
4. **包管理器**：第三方模块的安装与管理
5. **WebAssembly 后端**：在浏览器中运行 MiniLang

## 七、常见陷阱与规避策略

### 陷阱 1：演示时遇到 Bug
**规避**：
- 提前录制演示视频作为备份
- 选择经过充分测试的演示脚本
- 遇到 Bug 时诚实说明："这是一个已知问题，修复方案是..."

### 陷阱 2：被问到不了解的技术细节
**规避**：
- 诚实回答："这个细节我需要进一步研究，我的理解是..."
- 转移到熟悉的领域："不过 related 的 XXX 方面，我是这样处理的..."

### 陷阱 3：超时
**规避**：
- 提前演练并计时
- 准备精简版演示路线（3 分钟应急版）
- 演示时注意评委的时间提示

### 陷阱 4：现场环境问题（投影不清晰、软件崩溃等）
**规避**：
- 提前 30 分钟到场测试设备
- 准备纸质版代码截图（极端情况下展示）
- 保持冷静，寻求技术人员帮助
