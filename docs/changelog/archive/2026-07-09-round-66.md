## 2026-07-09 · 第六十六轮：关闭程序 UAF 根因修复（P0 × 2 + P1 × 2，共 4 项）

### 概述

本轮针对用户反复反馈的**关闭程序时读取访问权限冲突崩溃**（`this 是 0x1C7B339EB30`）进行彻底根因排查。系统化审计 closeEvent / ~Ide 析构链 / WorkerManager / VmStepper / IdeController 4 个协作成员的析构顺序与 QueuedConnection 残留，定位 4 项 UAF 根因并修复。核心发现：**`removePostedEvents(this, 0)` 的第二参数 `0` 表示 `QEvent::None`（几乎不存在的事件类型），并非"所有事件"**——这意味着此前所有的"清空待处理事件"防御实际均无效。MSVC 19.51 + Qt 6.10.3 + Ninja 构建通过，全量 1768/1768 测试通过。

### 关键设计决策

1. **`removePostedEvents` 无参版本清空所有事件类型**：Qt6 文档中 `removePostedEvents(QObject*, int)` 的第二参数是事件类型过滤器，`0` = `QEvent::None`（几乎不存在），`-1`（默认）= 所有类型。原代码 `removePostedEvents(this, 0)` 实为 no-op，是最致命的隐性 bug——所有"清空待处理事件"的防御均未生效。
2. **clearPendingEvents 覆盖 IdeController 全部 5 个对象**：IdeController 持有 pipeline_/workerMgr_/debugCoord_/vmStepper_ 4 个协作成员，任一成员的待处理事件在析构链中被 dispatch 都会 UAF。`clearPendingEvents()` 一次性清空 IdeController 自身 + 4 个协作成员的事件队列。
3. **QPointer 替代裸 this 捕获**：WorkerManager 析构顺序早于 interpreter_（shared_ptr 存活），裸 this 捕获的 lambda 在 WorkerManager 析构后仍可能被调用。QPointer 在 QObject 析构时自动置 null，lambda 检测后安全 no-op，与已有的 buildInputCallback 模式对齐。

### 关键教训

1. **`removePostedEvents(obj, 0)` 是常见 API 误用**——开发者常误以为 `0` 表示"所有事件"，实际 `0` 是 `QEvent::None`。正确用法是无参版本 `removePostedEvents(obj)`（默认 -1 = 所有类型）。
2. **Qt6 disconnect 不移除已投递事件**——`disconnect()` 仅断开未来投递，已入队的 `QMetaCallEvent` 仍会被 dispatch。closeEvent/析构路径必须 `disconnect` + `removePostedEvents` 双重保险。
3. **析构顺序敏感的回调必须用 QPointer**——当对象 A 持有 shared_ptr<B> 且 A 析构早于 B 时，B 中捕获 A 裸指针的回调会在 A 析构后悬垂。QPointer 自动置 null 是最安全的模式。
