## 2026-07-09 · 第六十四轮：P1/P2 级遗留问题批量修复（P1 × 4 + P2 × 5，共 9 项）

### 概述

本轮针对审计中标记的 9 项 P1/P2 级遗留问题进行系统性修复，覆盖三后端一致性（break/continue finally 续跳）、条件断点安全（超时机制）、断点行号跟踪（多行编辑偏移）、super 上下文正确性（定义类 vs 搜索起始类）、闭包变量写回、沙箱隔离、类型注解扩展、AST 位置信息完善、upvalue 关闭错误处理。核心成果是**新增 OP_PUSH_JUMP_TARGET/OP_FINALLY_END 指令对**，实现 break/continue 在 try-finally 内的"先执行 finally 再跳转"三后端一致语义。MSVC 19.51 + Qt 6.10.3 + Ninja clean rebuild 通过，1758/1759 测试通过（唯一"失败"为 `minilang_perf_test_NOT_BUILT` 占位符）。

### 关键设计决策

1. **OP_PUSH_JUMP_TARGET + OP_FINALLY_END 指令对而非编译期展开**：break/continue 在 try-finally 内的续跳可以用编译期展开（为每个 break/continue 复制 finally 块代码），但这会导致代码膨胀且不支持多层嵌套。运行时 pendingJumpStack_ 方案更紧凑，且多层嵌套只需从外到内依次 push。
2. **异常路径 finally 末尾不追加 OP_FINALLY_END**：异常路径的 finally 由 throwException 触发，执行完毕后应 re-throw（OP_THROW），而非续跳。break/continue 已被异常中断，pendingJumpStack_ 已清空。
3. **IR 路径用 label 而非 ip**：IR 是抽象层，不应依赖具体字节码偏移。finallyEntryLabel 在 visitTryStmt 进入时分配，break/continue 可直接引用，无需 deferred patch。
4. **条件断点步数上限而非时间超时**：步数计数是确定性的，不受 CPU 速度影响。10000 步足够覆盖合理的条件表达式，超限返回 false（不触发断点）比冻结 UI 更安全。

### 关键教训

1. **增量构建 ABI 不一致会导致大量假失败**：修改 .h 文件（如 Formatter.h 添加 lastNodeEndLine_ 成员）后，增量构建可能不重新编译所有依赖文件，导致 ABI 不一致引发 0xc0000005 崩溃。修改头文件后应使用 `--clean-first` 或手动清理相关 .obj 文件。
2. **break/continue finally 续跳需要编译期 + 运行时协同**：编译期维护 tryFinallyStack_ 上下文栈记录 finallyEntryIp 和待回填 patches，运行时维护 pendingJumpStack_ 存储真实跳转目标。两者缺一不可。
3. **多层 try-finally 嵌套续跳顺序**：从外到内依次 push（breakTarget → B.finallyEntry → A.finallyEntry），执行顺序从内到外（A.finally → pop B.finallyEntry jump → B.finally → pop breakTarget jump → breakTarget）。

## 2026-07-09 · 第六十三轮：ADS 标签蓝底问题 + 字节码背景 + 面板大小持久化根因修复（P1 × 3，共 3 项）

### 概述

本轮针对用户反馈的三个 IDE 视觉/交互问题进行根因修复：(1) dock 标签（资源管理器/调试/学习中心/打开文件）在 focused 状态下显示蓝色背景+米黄字体，非常突兀；(2) 编译分析面板的字节码子页面背景未变为米黄色；(3) 资源管理器/调试/学习中心/编译分析面板初始大小每次启动都被重置。三个问题均触及前几轮修复未发现的深层根因。MSVC 19.51 + Qt 6.10.3 + Ninja 构建通过，1720/1768 测试通过（48 项 formatter 审计测试为先前已存在的失败，与本轮 UI 修改无关）。

### 问题与修复对应表

| # | 严重性 | 类型 | 位置 | 修复内容 |
|---|--------|------|------|----------|
| 1 | P1 | ADS 内置 CSS 覆盖自定义 QSS（根因修复） | `app/ide.cpp` applyFluentStyle ADS QSS 应用 + 全局 palette | **dock 标签蓝底+米黄字体**——ADS 的 `loadStylesheet()`（由 `setColorSchemeMode` 触发）调用 `dockManager_->setStyleSheet(内置CSS)`，这是 widget 级别样式，优先级高于 qApp 级别。导致我们在 qApp 设置的 ADS QSS 被内置 CSS 覆盖。内置 `focus_highlighting.css` 中 `ads--CDockWidgetTab[focused="true"] { background: palette(highlight); }` 使用 `QPalette::Highlight`——系统默认蓝色，这就是 dock 标签蓝底的根因。根因修复三管齐下：(1) **在 dockManager_（widget 级别）追加自定义 QSS**——先调用 `setColorSchemeMode` 触发 `loadStylesheet`，然后将 adsQss 追加到 dockManager_ 的 styleSheet 上，后声明的同名选择器覆盖先声明的；(2) **设置 QPalette::Highlight 为主题 accent 色**（#268BD2），替代系统默认蓝色，同时设置 QPalette::HighlightedText 为米黄色；(3) **dockManager_ 也设置 palette**，确保 ADS 内部控件使用正确的 highlight 色。 |

### 失败原因总结（为何前几轮修复无效）

1. **标签蓝底问题（第 60 轮）**：第 60 轮在 qApp 级别设置了 ADS QSS，但不知道 ADS 的 `setColorSchemeMode` 会触发 `loadStylesheet()` 在 dockManager_（widget 级别）设置内置 CSS，优先级高于 qApp。必须在 dockManager_ 级别覆盖内置 CSS。
2. **面板大小问题（第 60 轮）**：第 60 轮的条件化默认尺寸（`hasSavedLayout_`）和 splitter 持久化方向正确，但没有发现 `restoreState` 在构造函数中（窗口 show 前）调用的时机问题——ADS 在无效几何下静默失败，恢复的尺寸不正确。必须在 showEvent 中执行 restoreState。

### 关键决策

- **dockManager_ 级别覆盖 vs 禁用 FocusHighlighting**：禁用 ADS 的 `FocusHighlighting` config flag 可以避免 focused tab 的蓝色背景，但也会失去焦点指示功能。在 dockManager_ 级别追加 QSS 既覆盖内置 CSS 又保留焦点指示（使用我们的 accent 色而非系统蓝色），是更优方案。
- **QPalette::Highlight 设置**：ADS 内置 CSS 使用 `palette(highlight)` 作为 focused tab 背景。设置 QPalette::Highlight 为 #268BD2（Solarized blue）后，即使内置 CSS 生效，背景也是主题蓝而非系统默认蓝。同时设置 HighlightedText 为米黄色确保对比度。
- **showEvent 延迟 restoreState vs QTimer::singleShot**：showEvent 在窗口首次显示时触发，此时几何尺寸已有效。比 QTimer::singleShot(0) 更可靠（后者在事件循环开始时触发，但窗口可能尚未完成布局）。
- **dock resize 事件过滤**：ADS 无 splitterMoved 信号。安装 eventFilter 捕获 dockManager_ 的 Resize 事件是检测面板大小变化的可靠方式。防抖 500ms 避免拖拽过程中频繁保存。

### 关键教训

1. **Qt 样式表优先级：widget 级别 > application 级别**：`dockManager_->setStyleSheet()` 的优先级高于 `qApp->setStyleSheet()`。第三方库（如 ADS）在 widget 级别设置的内置样式会覆盖 application 级别的自定义样式。必须在同一级别或更高级别覆盖。
2. **ADS restoreState 需要有效窗口几何**：`CDockManager::restoreState()` 内部使用容器几何尺寸计算 splitter 比例。在窗口 show 之前调用时几何无效，恢复静默失败。必须在 showEvent 或之后调用。
3. **palette(highlight) 是系统默认蓝色**：Qt 的 QPalette::Highlight 默认是系统主题色（Windows 上为蓝色）。自定义主题必须显式设置 QPalette::Highlight，否则使用 palette(highlight) 的控件会显示系统蓝色。
4. **QFluent registerWidget 与 setStyleSheet 冲突**：QFluent 的 `StyleSheet::registerWidget` 注册的控件在主题变化时重新应用 QFluent 样式（如 `background: transparent`），可能覆盖自定义 setStyleSheet。需要显式设置 objectName 并在白名单中强制覆盖。

### 关键决策

1. **P3.3 envPool_ cap=64 而非更大值**：正常场景 pool 大小受源码嵌套深度限制（Parser 深度上限 512），但实际教学代码嵌套很少超过 5-6 层。cap=64 远超实际需求，仅作为异常场景防御。超过 cap 时直接析构（shared_ptr 引用计数归零），不影响正确性，只是该次不回收至池。
2. **P3.4 loader 层返回 "\n" 而非改后端语义**：P3.13 曾改后端将空源码视为合法空模块，但 production loader 用空字符串表示"文件不存在"，导致 import "nonexistent" 静默成功。本轮在 loader 层区分：文件存在但为空返回 `"\n"`（非空字符串），文件不存在返回 `""`。三后端 `source.empty()` 检查不变，测试 helper 返回 `""` 的约定不受影响。改动面最小（3 处 loader lambda 各加 2 行），无需改后端或测试。
3. **P3.6 sendPostedEvents + repaint 而非保留 processEvents**：processEvents(ExcludeUserInputEvents) 会派发 QTimer 事件，各面板虽有 isVmRunning() 守卫但重入仍是风险。sendPostedEvents(DeferredDelete) 仅处理 QObject 删除，不派发 QTimer/Socket。repaint() 同步处理 paint event 不进入事件循环。组合使用既保持 UI 响应又彻底排除定时器。qobject_cast 安全降级：非 GUI 环境（测试）跳过 repaint。
4. **P3.7 try_lock 而非合并原子状态**：合并 paused_/stopped_ 为单一 atomic<int> 需重构所有 set 站点，改动面大。try_lock 利用现有 pauseMutex_——pauseExecution 持锁期间正是调试器暂停期间，try_lock 失败即意味着暂停。锁成功时一致读两个字段。try_lock 不阻塞 UI 线程，无死锁风险（pauseExecution 的 CV wait 会释放锁）。

### 关键教训

1. **loader 层修复优于后端语义修改**：P3.13 失败教训是改后端空源码语义会破坏 loader 的"空字符串=不存在"约定。在 loader 层区分"不存在"和"空文件"（返回不同值）是最小改动——后端和测试 helper 的约定不变。区分应在最接近信息源的层级完成。
2. **processEvents 的定时器重入是 Qt 6 已知限制**：ExcludeTimers flag 仅 X11 可用。替代方案是避免 processEvents，改用 sendPostedEvents + repaint 组合。repaint() 同步绘制不进入事件循环，是 UI 响应的安全替代。所有长循环让出点都应审查 processEvents 的必要性。
3. **try_lock 是无阻塞一致快照的标准模式**：当两个字段的原子组合需要一致性，且 mutex 可能在长时间操作（CV wait）中被持有时，try_lock 是标准模式——锁成功得一致快照，锁失败根据持锁语义推断状态。比合并原子状态改动面小，比加锁阻塞更安全。
4. **防御性上限应基于实际需求而非理论上限**：envPool_ 理论上限是 Parser 深度 512，但实际教学代码嵌套很少超过 5-6 层。cap=64 远超实际需求，作为异常场景防御。防御性上限不必等于理论上限，只需覆盖正常场景并阻止异常增长。

### 关键决策

- **三面板联动问题统一根因修复（Issue 3/4/6）**：三个看似独立的问题共享同一根因——`ensureEditorVisible()` 无条件切换到编辑器独占模式破坏三栏共存状态。一次性修复 `ensureEditorVisible`（保留三栏布局分支）+ `showTeachingPanel`（扩展动画触发条件）解决全部三个问题，避免分散补丁。
- **UAF 修复优先 disconnect 时机而非扩大守卫覆盖**：守卫是被动防御（lambda 被调用时检查），disconnect 时机是主动防御（不让 lambda 被调用）。第 57 轮 P0 修复只扩大守卫覆盖但 disconnect 时机未改，仍有时间窗漏洞。本轮将 disconnect 提前到 `closing_ = true` 之后立即执行（早于 maybeSave），从根本上消除时间窗，并辅以 5 个守卫作为双重保险。
- **教学库扩充时严格校验分类合法性与关键字段非空**：新增 OpCode 条目使用非法分类（bool/compare/stack/io/member/exception）触发 `CategoriesValid` 测试失败；closure-as-param 的 `capturedVars={}` 与 `captureType` 不含 "upvalue" 触发 `CriticalFieldsNonEmpty` 与 `CaptureTypeIsUpvalue` 测试失败。修复时严格按测试集合 {const, arith, var, control, call, container, closure, class} 重映射分类，并重写 closure-as-param 为 `makeAdder(n)` 模式确保字段满足约束。
- **GlossaryPanel 跳转语义分离**：`anchorClicked` 用于面板内导航（点击关联术语在当前面板内切换显示），`itemDoubleClicked` 用于跨面板跳转（双击列表项跳到其他教学面板）。原实现两者混用导致跳转异常，分离后语义清晰。

### 关键教训

1. **P0 修复必须审查 disconnect 时机而非只扩大守卫覆盖**：UAF 根因是「lambda 被调用时对象已析构」，守卫只能在被调用时检查，但 disconnect 时机决定了「lambda 是否会被调用」。disconnect 晚于可能触发 processEvents 的操作（如模态对话框）就存在时间窗。P0 修复应优先把 disconnect 提前到最早时机（`closing_=true` 之后立即），再以守卫作为双重保险。
2. **三面板联动问题应统一审查根因而非分散修复**：Issue 3/4/6 表现为不同症状（关闭编辑器误关教学区、打开编辑器后打不开学习面板、实验手册触发示例后内容消失），但根因都是 `ensureEditorVisible()` 无条件破坏三栏共存状态。分散修复会重复改动同一函数导致回归风险，统一根因修复更稳健。
3. **教学库扩充必须同步检查测试约束**：新增数据条目时不仅要保证内容正确，还要满足现有测试的约束（分类合法集合、关键字段非空、特定关键字必须包含）。扩充前应先读测试文件了解约束，避免扩充后测试失败再返工。
4. **anchorClicked 与 itemDoubleClicked 语义应分离**：Qt 中 `anchorClicked` 是链接点击信号，`itemDoubleClicked` 是列表项双击信号。两者都可用于触发跳转，但混用会导致行为冲突。明确分工：anchorClicked 面板内导航，itemDoubleClicked 跨面板跳转。

### 失败原因总结（为何前两次修复无效）

1. **背景色问题（第 57/58 轮）**：白名单枚举式方法是「打地鼠」模式——每发现一个未覆盖的区域就加一个 objectName 到白名单。根因是**缺少全局兜底**+**样式化时机错误**（applyFluentStyle 在 restoreLayout 之前执行）。只有全局 palette 兜底 + restoreLayout 后重新样式化才能彻底解决。
2. **面板大小问题（第 57 轮）**：只提升了最小尺寸和初始 resize 值，但没注意到 `QTimer::singleShot(0)` 的执行时机问题——它在 `restoreLayout` 之后触发，覆盖了恢复的尺寸。根因是**默认尺寸应用条件错误**（无条件 vs 仅无保存状态时）+**内部 splitter 尺寸未持久化**。

### 关键决策

- **全局 palette 兜底 vs 扩大白名单**：全局 palette + autoFillBackground 是 Qt 标准的背景传播机制，所有未显式设置背景的子 widget 自动继承父窗口的 palette。比白名单枚举式更健壮——新增容器无需手动加白名单即可继承背景色。白名单仅保留用于需要 `border:none` 等额外样式的容器。
- **restoreLayout 后重新 applyFluentStyle**：`dockManager_->restoreState()` 可能创建新的 dock 容器/分割器，这些新 widget 在 initUI→applyFluentStyle 阶段不存在。在 restoreLayout 后追加一次 applyFluentStyle 确保新容器也被样式化。
- **条件化默认尺寸 vs 移除默认尺寸**：完全移除默认尺寸会导致首次启动用户看到极小的面板（仅最小宽度）。条件化方案（`hasSavedLayout_` 标记）平衡了首次体验和持久化——首次启动用合理默认值，后续启动恢复用户保存的尺寸。
- **持久化内部 splitter 尺寸**：`centerSplitter_`（教学面板 vs 编辑器）和 `editorSplitter_`（编辑器 vs 底部面板）的尺寸此前不保存，用户调整后重启即丢失。新增 QSettings 键值 `layout/centerSplitterSizes` 和 `layout/editorSplitterSizes` 持久化。

### 关键教训

1. **白名单枚举式样式化是反模式**：每加新容器就要手动加白名单，遗漏即出问题。应优先使用全局 palette 兜底 + autoFillBackground，白名单仅用于需要额外样式的容器。
2. **QTimer::singleShot(0) 的执行时机陷阱**：`QTimer::singleShot(0, ...)` 在事件循环启动后才触发，如果它被调度在 `restoreLayout` 之前，但 `restoreLayout` 是同步执行的，那么 QTimer 会在 `restoreLayout` 之后触发，覆盖恢复的值。必须在 `restoreLayout` 内部条件化应用默认值。
3. **ADS saveState 不保存 dock 内部 widget 的 splitter 尺寸**：`dockManager_->saveState()` 只保存 dock 布局（哪些 dock 可见、位置、dock 间分割比例），不保存 dock 内部 widget 的 QSplitter 尺寸。需要单独持久化。
4. **反复修复同一问题时应审查根因而非补丁**：第 57/58 轮两次修复背景色都是「加白名单」，第 57 轮修复面板大小都是「提升最小尺寸/初始 resize」。这些是症状层补丁，没有触及根因（缺少全局兜底 / QTimer 覆盖恢复值）。反复修复同一问题时应停下来审查根因。

## 2026-07-09 · 第五十四轮审计：GC 栈溢出修复 + 未覆盖区域 Bug 排查 + 性能优化（P1 × 1 + P2 × 2 + P3 × 1 + Perf × 3，共 7 项）

### 概述

本轮聚焦前 53 轮未覆盖的 Bug 区域（GC 深嵌套栈溢出、模块路径 hash 一致性、REPL 多行历史）与性能优化机会。P1 级修复 GcManager markValue 纯递归遍历在深嵌套容器链（如 100000 层 `[[[[...]]]]`）下的栈溢出风险，改为显式 worklist 迭代式，同时消除递归调用开销（一举两得）。P2 级修复 ModuleIsolation pathHash 未折叠连续 `/` 导致同一模块产生不同 hash、ReplPanel 多行输入历史仅保存首行导致 Up 键无法恢复完整多行输入。P3 级修复 REPL 历史去重（连续相同命令不重复追加）。性能优化 3 项：DebugController RUN 快速路径移除冗余原子操作、IdeController notifyVmStateChanged 消除 vector 拷贝、Lexer string() 批量扫描连续普通字符。MSVC 19.51 + Qt 6.10.3 + Ninja 构建通过，全量 1763/1763 测试通过。

### 问题与修复对应表

| # | 严重性 | 类型 | 位置 | 修复内容 |
|---|--------|------|------|----------|
| 1 | P1 | 栈溢出 | `interpreter/GcManager.cpp` markValue | **markValue 纯递归遍历深嵌套容器链栈溢出**——原实现对 ARRAY/DICT/INSTANCE/CLOSURE 四种堆类型纯递归遍历子元素。MiniLang 的 MAX_LOOP_ITERATIONS=10000000 允许 while 循环构建极深嵌套的线性容器链（如 100000 层 `[[[[...]]]]`），这条链不是循环引用（每层不同对象），GC mark 阶段递归深度等于链长度，触发栈溢出崩溃。修复：改为显式 worklist 迭代式——`std::vector<const Value*> worklist`，将子元素 push_back 到 worklist 而非递归调用，栈深度恒定。同时解决递归调用开销（Perf 双重收益）。 |
| 2 | P2 | 路径一致性 | `ast/ModuleIsolation.cpp` pathHash | **pathHash 未折叠连续 `/`**——`"./a//b"` 与 `"./a/b"` 经 normalize（`\`→`/` + 去 `./` 前缀）后仍含 `//`，FNV-1a hash 产生不同值，导致同一模块被当作两个不同模块，`__mod_<hash>__` 前缀不一致引发重命名解析失败。修复：normalize 阶段后增加连续 `/` 折叠（保留单个 `/`）。 |

| 5 | Perf | 原子操作 | `debug/DebugController.cpp` checkBreak | **RUN 快速路径冗余原子操作**——原 D-P1-1 快速路径（RUN 模式 + 无断点）在返回前调用 updateLineTracking，每节点执行 2 次原子 load（line/lastSeenLine_）+ 1-2 次原子 store（crossedLine_/lastSeenLine_）。紧密循环百万级节点累积可观开销。修复：移除快速路径的 updateLineTracking 调用。快速路径前提是无断点，crossedLine_/lastSeenLine_ 不被任何逻辑读取；用户添加断点后 hasBreakpoints_ 变 true 进入慢速路径，updateLineTracking 会重新计算。回退 D-P2-11 fix。 |
